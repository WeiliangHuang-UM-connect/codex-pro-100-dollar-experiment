# 过程复盘

## 初始条件

用户提出让 AI 自主赚到 100 美元，允许持续尝试。现有 GitHub 登录可用；最初收款渠道是支付宝，随后用户自行设置 MetaMask，并优先选择加密货币收款。助手没有独立账户替用户代收。

本次有人参与：用户完成账户和钱包操作，对指定买方的申请及 GitHub 询问作了明确批准。因此不能把这个实验写成“给 AI 一个目标后，人完全不再参与”。

## 找订单的成本

公开悬赏里同时混着有效需求、已有人接手的任务、示例金额、卖方广告、积分奖励和过期页面。最耗时的工作之一，是查清楚“谁会付钱、付给谁、凭什么验收”。

Chain.Love 就是一个具体例子：奖励机制看起来清晰，但扫描开放 PR 后，可选方向已有重叠。源码能改、字段能补，并不代表这些变化有人会付费购买。

中文路线也类似：程序员客栈的签约条件、部分平台的付费沟通入口、已接包的 V2EX 帖子，都限制了即时接单。支付宝可用并不能省去买方和平台的准入要求。

## 登录调试：错误确实有一部分在助手侧

BountyBook 登录一度报 `Unexpected login message; signing disabled`。本地校验器最初只接受文档中的长消息格式，接口实际返回的是紧凑 nonce 格式。

后续改成严格匹配两种允许格式，并验证畸形消息会被拒绝；没有直接取消签名内容校验。另一个独立问题是钱包存在待处理请求，授权页面与当前浏览器状态不同步。用户多次说“已经授权”，不能据旧页面状态反复归因给用户。

登录最终成功，说明障碍不是“永远无法使用钱包”。但这也暴露出人工交接和会话状态管理的成本。

## 本地通过，不等于平台验收

Dijkstra 代码通过公开验收用例以及自编测试，包括与独立 Floyd–Warshall 实现比较随机图结果。实际提交顺序如下：

| 次序 | 交付包装 | 平台结果 |
| --- | --- | --- |
| 1 | files 字典与说明 | 代码被解析为仅 2 行 |
| 2 | files 数组，path/content | 同样的行数错误 |
| 3 | 文件名直接映射源码 | 在 ipfs_fetch 阶段报 undefined.length |
| 4 | filename/language/code | 同样的内部异常 |

四次都使用同一份经过测试的源码。不能仅凭这些响应确定根因完全在平台；可以确定的是：服务器没有接受交付，任务又回到开放状态，没有付款记录。达到这个证据边界后停止，不用更多失败请求伪装进度。

核查平台过去的付款记录有助于判断是否值得试单，但别人的历史交易从来不算本实验收入。

## 参与资格与客户需求

Ubiquity 两个任务的标价合计超过目标，但当前账户只有读取权限，机器人限制协作者参与。实际动作是一条诚实询问，披露 AI 辅助，并等待资格确认。没有拿标价之和冒充已赚金额。

LaborX 的剪辑任务把路线从代码悬赏转向真实客户服务。申请提出明确价格、工期、一次修改和 AI 辅助披露，并在开工前索要素材、风格与使用授权。买方接受和托管入金都尚未发生。

用户用 Google 注册并不需要重来。LaborX 官方说明允许使用其他注册方式后再接 MetaMask。之后出现的 Chrome 控制接口错误，应记录为工具故障，不能误判为账户注册错误。

后续用户明确选择在 Codex 内置浏览器登录，页面操作恢复可用。申请还要求至少添加技能，保存资料又要求国家/地区；助手填写已有样例支持的 Python、Data Processing、Scripting，地区由用户确认后选择。之后提交成功，My Jobs 显示完整申请、250 美元预算和 15 天工期。这里完成的是申请流程，买方尚未接受或付款。

## 可以从这次经历得出的结论

AI 已经能完成局部开发、测试、资料核验和申请起草。这个实验还没有证明它能在指定时间内独立找到买方并完成收款。当前暴露出的关键缺口是付费机会的真实性、平台准入、交付协议与人工交接，而不是缺少一份能运行的代码。

目标仍然是收入。文章和代码仓库是实验副产品，不能用它们替代到账目标。


## 从申请推进到技术交付

SABLE 回复改变了状态：此前只有报价，现在有明确买方预算、任务分配和可执行验收范围。技术部分已实际运行并交付，包含正常内容与重试对照、独立 JVM 读取和公开 CI。新的剩余环节是买方验收及可用收款渠道；任务开始前确认付款方式依然重要。成功复现不是收入，收款准备也不能假定。
